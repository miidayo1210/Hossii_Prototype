# 1. 概要

「Hossiiからの挑戦状」は、スペース管理者またはスーパー管理者が、スペース内に質問やミッションを設置し、参加者が回答または行動を達成する機能である。

参加者が質問・ミッションの達成条件を満たすと、その参加者のスタンプカードに、さまざまな表情や姿をしたHossiiが付与される。

付与されたHossiiはアカウント全体の「Hossiiコレクション」に蓄積される。

一連の質問・ミッションは「挑戦状ストーリー」としてまとめられ、参加者は自分の回答、写真、達成した行動、取得したHossiiを「自分の軌跡」として振り返ることができる。

📌 **クリア**はクリアに必要な項目の全達成、**コンプリート**はおまけを含む全項目達成とする（詳細は 13 / 26）。完了限定Hossiiは 🔭 未実装。

---

# 2. 開発目的

これまでのHossiiは、参加者が自由に投稿し、想いや行動を共有することを中心としてきた。

本機能では、自由投稿に加えて、主催者や管理者が問いや行動のきっかけを用意できるようにする。

目的は、参加者を管理・評価することではなく、以下を実現することである。

* 行動を始めるきっかけをつくる
* 学びや気づきを記録する
* 途中経過を含めた積み重ねを可視化する
* 心理的安全性を保ちながら回答できる
* Hossiiを集める楽しさによって継続を促す
* 自分の回答や達成を、個人の軌跡として振り返る
* 誰かと同じストーリーに取り組む感覚をつくる

# 3. 用語定義

## 3.1 挑戦状

参加者向けに表示される、個別の質問またはミッションの総称。

## 3.2 質問

考え、感情、経験、気づきなどの入力を求めるもの。

例：

* 今日、一番印象に残ったことは？
* 今の気持ちに近いものを選んでください
* 次にやってみたいことは？

## 3.3 ミッション

特定の行動や実践を求めるもの。

例：

* 初めて会った人に話しかける
* 気になった場所の写真を撮る
* チームメンバーへ感謝を伝える

## 3.4 挑戦状ストーリー

複数の質問・ミッションをまとめた一連のパッケージ。

例：

* 下妻アカデミー第1章
* 今日の学びを見つける5つの挑戦状
* 石蔵を知る10の挑戦状
* 30日アクション

DB正本テーブルは `challenge_programs`（✅。仮称ではない。4.4 / 29）。

## 3.5 スタンプカード

挑戦状ストーリーの達成状況を、Hossiiスタンプの集合として表示するUI。📌 役割は進捗表示に加え、挑戦の記憶を開く入口（14.5）。

## 3.6 Hossiiスタンプ

質問・ミッションを達成した時に付与される、さまざまな表情・ポーズ・装飾を持つHossii。

## 3.7 Hossiiコレクション

複数のスペースや挑戦状ストーリーを横断して、アカウントが取得したHossiiを一覧表示する機能（🟡／🔭。正本は `challenge_rewards`）。

## 3.8 自分の軌跡／挑戦の軌跡

参加者自身の回答、写真、選択内容、達成した行動、取得Hossii、おみくじ、開始日、完了日をまとめて表示する記録。

## 3.9 スペース管理者（参加者向け用語と現行実装の対応）

本仕様における表示名・役割名は「スペース管理者」とする。参加者向けUIにもこの名称を用いる。

現行実装上の対応は、次のとおりである。

* 本仕様におけるスペース管理者は、対象スペースが所属するコミュニティの管理者に対応する
* 権限判定の正本は、コミュニティ管理者の識別とスーパー管理者判定である
* 実装上の判定は、現行のスペース管理可否判定およびスペース所属コミュニティ管理者判定に対応する
* スペース所属レコード上の役割（メンバー／管理者など）は、本機能の一般管理権限判定には使用しない
* 将来、スペース固有の管理者が追加された場合は、本仕様の権限章を別途更新する

> **実装依存注記（参加者向けには露出しない）:**  
> 現行コード／DBでは、コミュニティ管理者の正本は `communities.admin_id`、スーパー管理者は JWT `app_metadata.role = 'super_admin'`、フロントの `canManageSpace` および DB の `is_space_community_admin` が対応する。`space_memberships.role` は本機能の一般管理権限には用いない。

## 3.10 発行参加ID

管理者がスペース向けに発行するログイン用アカウント。現行では通常の認証ユーザーとして扱われ、ゲストとは区別される。

挑戦状機能では、発行参加IDでログインした参加者もログイン済みアカウントとして扱う（詳細は 5.3）。

## 3.11 既存の `#card` スタンプとの区別

既存のスペース内 `#card` 画面に表示されるスタンプ機能は、投稿数などに基づく別機能である。

本仕様のスタンプカード（挑戦状ストーリーの達成進捗）とは、正本・進捗・UIを共有しない。

## 3.12 マイHossiiとの区別

既存のマイHossiiは、アカウントのHossii見た目設定である。

本仕様のHossiiコレクション（報酬付与履歴から導出する取得一覧）の正本にはしない。

# 5. 利用条件

## 5.1 ログイン

スタンプカード、Hossii取得、Hossiiコレクション、自分の軌跡を利用するには、ログイン済みアカウントを必須とする。

ゲスト参加者へのスタンプ付与や一時進捗保存は、初期実装では行わない。

## 5.2 未ログイン時

未ログイン状態で挑戦状を開いた場合は、以下を表示する。

> この挑戦状に取り組み、Hossiiを集めるにはログインが必要です。

その後、以下の導線を表示する。

* ログイン
* 新規登録

ログイン完了後は、元の挑戦状へ戻る。

## 5.3 発行参加ID

発行参加IDでログインした参加者も、認証済みアカウントとして扱う。

* 対象スペースに所属し、挑戦状ストーリーの対象者に含まれる場合は利用可能とする
* スタンプ、回答、軌跡、Hossiiコレクションは、当該認証ユーザーに紐づく
* 通常アカウントとの統合、アカウントマージ、報酬引き継ぎは今回のMVP対象外とする（将来対応）

* 本仕様におけるスペース管理者は、現行実装上、対象スペースが所属するコミュニティの管理者に対応する
* 権限判定の正本は、コミュニティ管理者識別とスーパー管理者判定である
* 現行のスペース管理可否判定／スペース所属コミュニティ管理者判定に対応する

* 将来スペース固有管理者が追加された場合は、権限仕様を別途更新する

コード名・テーブル名・関数名は実装依存情報として扱い、参加者向け用語には露出しない。

## 6.1 スーパー管理者

以下を実行できる。

* 全スペースの機能ON・OFF
* 全スペースの挑戦状ストーリー確認
* システム共通テンプレートの作成
* Hossiiスタンプ素材の登録・編集・停止
* レアリティ・抽選確率の管理
* おみくじ共通メッセージの管理
* 不具合対応に必要な監査情報の確認（ただし「自分だけ」回答への監査付き特別アクセスは、現行に存在しないため本仕様の前提にしない。詳細は 20.1）

## 6.2 スペース管理者

自身が管理するスペースにおいて、以下を実行できる。

* 挑戦状ストーリーの作成・編集・複製
* 質問・ミッションの作成
* 回答形式の設定
* 対象者の設定
* 公開範囲の設定
* Paneへの設置
* スタンプカードの表示設定
* 回答・進捗確認（「自分だけ」の回答を除く）
* 管理者承認
* ストーリーの公開・終了・アーカイブ

「自分だけ」に設定された回答は、通常のスペース管理者画面からも閲覧できない。

## 6.3 参加者

以下を実行できる。

* 対象となっている挑戦状ストーリーの閲覧

* 自分の回答の確認・修正
* スタンプカードの閲覧
* Hossiiコレクションの閲覧
* 自分の軌跡の閲覧

発行参加IDでログインした参加者も、対象者に含まれる場合は本節の権限を持つ。

# 7. スペース単位の機能ON・OFF 🟡

🟡 Production未実装。現在のナビ表示は「published な挑戦状が1件以上あるか」で制御する（✅）。

スペースごとに、挑戦状機能全体をON・OFFできる想定である。保存先（スペース設定か Feature Flag か）は ❓。

## 7.1 ONの場合

* ナビゲーションに「挑戦状」を表示する
* 挑戦状ストーリーを表示する
* Pane内に質問・ミッションを設置できる
* スタンプカードを表示できる
* Hossiiを付与できる
* 自分の軌跡を表示できる

## 7.2 OFFの場合

* ナビゲーションの「挑戦状」を表示しない
* Pane内の質問・ミッションを表示しない
* スタンプカードを表示しない
* 新規回答を受け付けない
* 既存回答、達成記録、取得Hossiiは削除しない
* 管理者が再度ONにした場合は既存状態を復元する

OFFのスペースでは、参加者から見て質問・ミッションモード自体が存在しない状態にする。

# 9. 挑戦状ストーリー

## 9.1 基本項目

管理者は以下を設定する。

| 項目         | 必須 | 内容              |
| ---------- | -: | --------------- |
| タイトル       | 必須 | 参加者向け名称         |
| 導入文        | 任意 | 目的やストーリー説明      |
| カバー画像      | 任意 | 一覧表示用画像         |
| 対象スペース     | 必須 | 配信先スペース         |
| 対象者        | 必須 | 全員、指定アカウント、管理者を除く参加者（指定グループは将来） |
| 公開状態       | 必須 | 下書き、公開、終了、アーカイブ |
| 公開開始日時     | 任意 | 表示開始日時          |
| 回答終了日時     | 任意 | 回答受付終了日時        |
| 進行方式       | 必須 | 自由順、順番固定        |
| 完了条件       | 必須 | 必須項目をすべて達成      |
| 完了メッセージ    | 任意 | 完了時の文章          |
| スタンプカード    | 必須 | ON・OFF          |
| Hossii付与   | 必須 | ON・OFF          |
| おみくじ       | 必須 | ON・OFF          |
| 完了限定Hossii | 任意 | 付与するHossii      |
| Pane設置     | 必須 | ON・OFF          |

## 9.2 複数ストーリー

1つのスペースに複数の挑戦状ストーリーを作成できる。

参加者が「挑戦状」を開くと、以下の区分で表示する。

* 進行中
* これから
* 完了
* 過去の挑戦状

## 9.3 対象者

対象者設定を、個別アカウントON・OFFより優先する正本とする。

### 最終仕様で選択できる対象

管理者は以下を選択できる。

* スペース参加者全員
* 指定アカウント
* 指定グループ（将来対応。現行にグループ実体が無いため MVP では提供しない）
* 管理者を除く参加者

さらに、個別アカウントを対象から除外できる。

対象外の参加者には、以下を表示しない。

* ストーリー
* 質問・ミッション
* スタンプカード

### MVPでの対象者

MVPでは、次のみを対象とする。

* スペース参加者全員
* 指定アカウント
* 管理者を除く参加者
* 個別アカウントの除外

「指定グループ」は将来対応とする。最終仕様からは削除しない。

発行参加IDでログインした認証ユーザーも、スペースに所属し対象者に含まれる場合は対象とする。

## 9.4 複製

管理者は既存ストーリーを複製できる。

複製するもの：

* 基本設定
* 質問・ミッション
* 回答形式
* 表示順
* Pane配置
* スタンプカード設定
* 完了設定

複製しないもの：

* 参加者の回答
* 達成記録
* 取得Hossii
* 参加者別進捗
* 専用URL・QRトークン

# 11. 回答形式

## 11.0 追加優先順位 📌

正式な実装順は次のとおり。DB上の `response_type` 名と利用者向け呼称を併記する。

# 13. クリアに必要／おまけと、クリア／コンプリート 📌

内部・DB上の概念は必須（`is_required = true`）／任意（`false`）のままとする。

参加者・管理者向けの表示文言は次に統一する。

* 必須項目 → **クリアに必要**
* 任意項目 → **おまけ**

「必須」単独表記を利用者向けUIに残さない（進捗サマリー含む。残存は技術負債／follow-up）。

## 13.1 クリア 📌

**クリア**＝クリアに必要な項目をすべて達成した状態。

| 条件 | 結果 |
| --- | --- |
| クリアに必要な項目が1件以上あり、そのすべてを達成 | ✅／📌 クリア |
| クリアに必要な項目が0件で、項目が1件以上あり、全項目を達成 | ✅／📌 クリア（現行実装の扱い。全項目＝この場合コンプリートと一致） |
| 項目が0件 | クリアではない |

一覧・Modal・スタンプで「クリア」と「コンプリート」を混同しない。

表示候補：**クリア済み**（「Complete」単独表記は必須仕様にしない）。

## 13.2 コンプリート 📌

**コンプリート**＝おまけを含む全項目を達成した状態。

クリア後におまけが残る場合は、クリア済みかつ未コンプリートとして扱う。

表示候補：**コンプリート**。

## 13.3 おまけ

おまけはクリア条件に含めない。達成時も通常どおりHossiiを付与する（✅ 初回のみ）。

例：

* クリアに必要5＋おまけ2 → 必須5達成でクリア、全7達成でコンプリート

テンプレート例：

* 1〜5個：大きめの自由配置

* 21〜30個：道、星座、足跡型
* 31〜50個：複数ページまたは区画分割

管理者は配置テンプレートを変更できる。

MVPでは、スタンプごとの自由座標編集は行わない。

# 16. Hossiiレアリティ 🔭

レアリティは以下の4段階とする。

| 内部名称       | 参加者向け名称       |
| ---------- | ------------- |
| normal     | いつものHossii    |
| rare       | ちょっと珍しいHossii |
| super_rare | とても珍しいHossii  |
| secret     | 特別なHossii     |

## 16.1 基本確率

初期確率を以下とする。

| レアリティ         | 基本確率 |
| ------------- | ---: |
| いつものHossii    |  80% |
| ちょっと珍しいHossii |  16% |
| とても珍しいHossii  | 3.5% |
| 特別なHossii     | 0.5% |

確率の合計は100%とする。

## 16.2 確率管理

抽選確率はスーパー管理者が管理する。

スペース管理者は確率を変更できない。

ストーリーごとに取得対象Hossiiを限定することはできる。

# 17. 達成によるレア確率上昇 🔭

同じ挑戦状ストーリー内で項目を達成するほど、レア以上の取得確率を上昇させる。

## 17.1 上昇ルール

ストーリー内の達成数に応じて、レア以上の確率へ補正を加える。

| ストーリー内達成数 | レア以上への補正 |
| --------: | -------: |
|       1〜2 |     補正なし |
|       3〜4 |   ＋2ポイント |
|       5〜9 |   ＋4ポイント |
|     10〜19 |   ＋7ポイント |
|      20以上 |  ＋10ポイント |

補正分は「いつものHossii」の確率から差し引く。

レア、スーパーレア、シークレットへの配分比率は、スーパー管理者設定に従う。

## 17.2 天井

レア以上を8回連続で取得できなかった場合、9回目はレア以上を確定する。

スーパーレアまたはシークレットを20回連続で取得できなかった場合、21回目はスーパーレア以上の確率を大きく上げる。ただし確定とはしない。

レア以上を取得した時点で、レア天井カウントをリセットする。

## 17.3 完了限定Hossii

ストーリーのすべての必須項目を達成した場合、通常抽選とは別に完了限定Hossiiを1体付与する。

完了限定Hossiiは重複抽選ではなく、ストーリーに設定されたHossiiを確定付与する。

# 18. おみくじ 🔭

## 18.1 概要

Hossii取得時に、Hossiiからの短い言葉としておみくじを付与する。

おみくじは参加者への評価ではない。

## 18.2 結果と確率

| 結果 |  確率 |
| -- | --: |
| 大吉 |  8% |
| 中吉 | 17% |
| 吉  | 30% |
| 小吉 | 22% |
| 末吉 | 20% |
| 凶  |  3% |

## 18.3 Hossiiとの関係

Hossiiのレアリティとおみくじ結果は別々に抽選する。

ノーマルHossiiでも大吉になることがあり、特別なHossiiでも末吉になることがある。

レアリティを人の価値や成果の良し悪しと結びつけない。

## 18.4 おみくじメッセージ

基本メッセージはHossii共通テンプレートとして、スーパー管理者が管理する。

スペース管理者は、挑戦状ストーリー固有の追加メッセージを設定できる。

表示例：

> 大吉！
> 新しい一歩が、次の出会いにつながりそう。
> 今日の好奇心を大切にしてみよう。

## 18.5 凶の表現

凶であっても、不安をあおる表現、失敗を断定する表現、人格を否定する表現は禁止する。

例：

> 今日は少し立ち止まる日かも。
> 焦らず、自分のペースで進もう。

## 18.6 結果の固定

おみくじはHossii付与時に1回のみ抽選し、再抽選しない。

### 既存回答 📌

回答が1件以上存在する公開中ストーリーには、新しい項目を追加できない。

* 旧版の回答を引き継がない

* スタンプの追加付与

管理者承認型の場合、内容を大きく修正した場合は再承認待ちとする。

## 24.2 参加者による回答削除

参加者が回答を削除した場合でも、取得済みHossiiは原則として保持する。

Hossiiは、一度取り組んだ軌跡として扱う。

ただし、回答データには削除済みであることを記録し、軌跡画面では削除済みとして表示するか非表示にする。

## 24.3 管理者による達成取消

誤操作、不正、重複処理などの理由で管理者が達成を取り消した場合は、対応するHossiiを回収できる。

回収時には以下を記録する。

* 取消者
* 取消日時
* 取消理由
* 対象Hossii
* 元の達成記録

参加者が通常の回答修正をしただけでは、Hossiiを回収しない。

# 25. 通常投稿との関係

質問・ミッションへの回答は専用回答データを正本とする。

既存の通常投稿データ（吹き出し投稿）を、回答の正本として使用しない。

回答者は、公開範囲に反しない場合に限り、回答を通常の吹き出し投稿として共有できる。

共有投稿は回答の複製表示であり、正本ではない。

以下を不変条件とする。

* 共有投稿を削除しても元回答は残る
* 元回答を修正しても共有投稿を自動上書きしない
* 元回答削除時は共有投稿の扱いを確認する
* 匿名回答は匿名のまま共有する
* 「自分だけ」「管理者だけ」の回答は通常投稿へ共有できない

# 30. 不変条件

以下は、他機能の変更によって意図せず変化してはならない。

1. 項目正本は `challenge_items`、回答は `challenge_responses`、達成は `challenge_completions`、報酬は `challenge_rewards`
2. UI専用の重複正本テーブルを作らない
3. 同一参加者・同一項目へ、許可されていない重複Hossii付与をしない
4. 初回のみ報酬付与する（回答更新・削除後の再回答では再付与しない）

6. 一度付与したHossiiを再表示時に変更しない
7. 公開後はストーリー構造を編集できない（draftのみ構造編集）
8. 参加者のプログラム／項目 SELECT は published かつ active member（管理者ポリシーは別）
9. RLSが閲覧境界を強制する（フロント非表示のみで公開範囲を実現しない）
10. `self_only` を通常の管理者へ表示しない（存在・件数とも）
11. スペース切替時に前スペースの挑戦状UI状態を残さない
12. Hossii画像の「登録」と「獲得可能性」を混同しない
13. 機能OFFや通常投稿の削除で、元の回答・報酬正本を失わない（将来ON/OFF実装時も）
14. 参加者の回答公開範囲を、回答後に一方的に広げない

# 1. UI設計原則

本機能は、管理・課題提出の印象よりも、Hossiiから問いや挑戦が届き、楽しみながら一歩ずつ進む体験を重視する。

## 1.1 参加者側

* 「やらなければならない」より「やってみたい」と感じられる
* 未達成を責める表現を使わない
* 現在地と次の一歩が分かる
* 回答前に公開範囲が分かる
* 回答後すぐにHossii獲得の喜びを感じられる
* 自分の回答と軌跡へ迷わず戻れる
* Hossiiの表情やコレクションを楽しめる
* 画面を情報で埋めすぎない
* 主要操作は片手で押しやすい位置に置く

## 1.2 管理者側

* Googleフォームを作成する程度の感覚で設定できる
* ストーリー全体と質問単位の設定を混同させない
* 公開前と公開後の状態を明確に分ける
* 誰に、どこで、何が見えるか確認できる
* 公開後に変更できない項目を事前に知らせる
* 回答、達成、公開範囲を安全に管理できる
* 高機能でも、一画面に設定を詰め込みすぎない

# 16. モックアップで検証する事項

ビジュアルモックアップ作成後、以下を確認する。

## 16.1 参加者体験

* 「挑戦状」の意味が初見で伝わるか
* 次に何をすればよいか分かるか
* 質問とミッションの違いが伝わるか
* 公開範囲を回答前に理解できるか
* スタンプカードが子ども向けに見えすぎないか
* Hossii獲得演出が過剰でないか
* レアリティが人の評価に見えないか
* 任意項目が本当に任意だと伝わるか
* 自分の軌跡を見返したくなるか

## 16.2 管理者体験

* ストーリーと個別質問の設定を区別できるか
* Googleフォームに近い感覚で項目を追加できるか
* 公開範囲の違いを理解できるか
* 公開後に変更できない項目が分かるか
* Paneへの設置方法が直感的か
* スタンプ数が自動生成されることを理解できるか
* 回答一覧と進捗管理を混同しないか
* 「自分だけ」の回答が見えないことを理解できるか

# 17. デザイン方向

## 17.1 共通

* ぷくっとした立体感
* シンプルで明るい
* 子どもっぽすぎない
* 大人も使える綺麗さ
* Hossiiの表情が主役
* 青空、星、光、軌跡を補助モチーフにする
* 文字や設定項目を装飾で埋めすぎない

## 17.2 参加者側

* 柔らかいカード
* 大きめの余白
* Hossiiの表情を感情的な報酬として使う
* 未達成枠は灰色にせず、淡い光やシルエットで表現
* 完了時のみ少し華やかにする

## 17.3 管理者側

* 参加者画面より装飾を抑える
* 設定項目は白背景の編集カード
* 選択状態を明確にする
* プレビュー部分のみ参加者向けデザインを表示
* 公開・削除・変更不可などの状態を色以外の文言でも示す
