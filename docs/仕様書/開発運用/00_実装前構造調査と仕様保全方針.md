# 実装前構造調査と仕様保全方針

> **分類:** `[Development / Architecture / Specification / Quality]`
> **ステータス:** ✅ 正本
> **適用範囲:** Hossiiのすべての調査・修正・機能追加・リファクタリング
> **目的:** ある機能の変更が、周囲の仕様・データ・権限・導線を意図せず壊すことを防ぎ、重複・矛盾・古い構造を段階的に整理する

---

## 1. 基本方針

Hossiiでは、機能を修正・追加する前に、対象箇所だけでなく、その機能を成立させている周辺構造を必ず調査する。

コード上で目に見える不具合だけを局所的に修正してはならない。

最初に、次を確認する。

* 現在の仕様
* 現在のコード
* DBの実構造
* RLS・RPC・trigger
* 状態管理
* キャッシュ・localStorage
* 関連する画面・導線
* IDや権限の対応
* データの作成・更新・削除経路
* 過去仕様との互換処理
* 関連テスト

調査後に、変更範囲を決定する。

---

## 2. 必須の実装順序

すべての修正・機能追加は、原則として次の順序で進める。

```text
1. 周辺構造調査
↓
2. 現在仕様と実装の比較
↓
3. 矛盾・重複・古い構造の整理
↓
4. 正本と不変条件の決定
↓
5. 最小差分の修正
↓
6. Development受入
↓
7. 回帰テスト
↓
8. 仕様書更新
↓
9. レビュー
↓
10. merge
↓
11. Production反映
↓
12. Production受入
```

調査を行わず、推測だけで実装を開始してはならない。

---

## 3. 実装前に確認する対象

### 3.1 仕様書

対象機能に関係する仕様書をすべて確認する。

確認事項：

* 同じ機能を複数の仕様書が定義していないか
* 正本仕様書が明確か
* 古い仕様が現在仕様として残っていないか
* 仕様書同士に矛盾がないか
* 実装済み・未実装・将来案が区別されているか
* 用語が統一されているか
* 今回変更する仕様と変更しない仕様が明確か
* 「閲覧可能」「所属表示」「membership行の存在」「投稿可能」を別概念として混同していないか

矛盾がある場合は、どの仕様書を正本とするか決める。

---

### 3.2 コード

対象画面だけでなく、データの取得・保存・復元・権限判定まで追跡する。

確認対象：

* Component
* Hook
* Context
* Store
* Utility
* API
* RPC呼び出し
* Route
* Auth処理
* localStorage / sessionStorage
* fallback
* error handling
* loading状態
* キャッシュ
* feature flag

データフローを、可能な限り次の形式で整理する。

```text
ユーザー操作
→ UI
→ Hook / Context
→ API / RPC
→ DB
→ 状態更新
→ 表示
```

各段階で、使用するIDと正本を明記する。

クライアント制御がある場合は、**RPCを直接呼び出した場合の越境**（UIを迂回した操作）も調査する。クライアント抑止だけで権限境界が閉じたと断定しない。

---

### 3.3 DB・権限

DB変更がない予定でも、関連するDB構造は確認する。

確認対象：

* テーブル
* 列
* 外部キー
* unique制約
* CHECK制約
* index
* trigger
* RPC
* function
* RLS
* policy
* SECURITY DEFINER
* GRANT / REVOKE
* Auth metadata
* migration履歴
* 関連するDevelopmentデータのread-only集計（件数・過剰所属・orphan等。実値・秘密情報はマスク）

Development DBの実定義とmigrationファイルが一致するかも確認する。

コード上のmigrationだけを見て、現在DBの状態を断定してはならない。

---

## 4. 必ず洗い出す問題

実装前調査では、次の問題が存在しないか確認する。

### 4.1 仕様の矛盾

例：

* 仕様書Aではスペース限定
* 仕様書Bでは複数コミュニティ所属
* コードは別の第三方式

この場合、実装を続ける前に正本を決める。

---

### 4.2 正本の重複

同じ意味の情報が複数箇所に存在する場合、どれを正本とするか決める。

例：

* `user_profiles.username`
* `profiles.default_nickname`
* `space_nicknames`
* `space_memberships.space_nickname`
* UI fallback

それぞれの役割を分け、同じ判定に複数の値を無秩序に使用しない。

---

### 4.3 似た役割の項目・テーブル

次の状態を洗い出す。

* 名前が違うが意味が同じ
* 名前が同じだが意味が違う
* 同じデータを複数テーブルで保持
* 古いテーブルと新しいテーブルが併存
* 表示用データと権限用データが混同
* 「閲覧可能」と「所属」が混同
* 「アカウント名」と「スペース内ニックネーム」が混同

---

### 4.4 未使用・古い構造

次を確認する。

* 現在使われていないComponent
* 呼ばれていないHook
* 古いRPC
* 古いテーブル
* 古いlocalStorageキー
* 廃止済みのfeature flag
* 旧導線
* 過去仕様の互換fallback
* 現在到達不能な画面
* 読まれているが書かれていない列
* 書かれているが読まれていない列
* migration上だけ残る定義

未使用と判断しても、同じPRで即削除しない。

今回削除するか、後続整理にするか、残す理由を明記する。

---

### 4.5 重複処理

確認事項：

* 同じRPCを複数箇所から呼んでいないか
* 同じ情報をContextとComponentで別々に取得していないか
* 同じ正規化処理が複数箇所にないか
* 同じplaceholder判定が複数実装されていないか
* 同じデータを複数APIから取得していないか
* 同じ保存処理を複数経路が持っていないか

可能な場合は正本となる取得・判定・保存処理を1つに集約する。

ただし、集約のための大規模変更を不具合修正へ混ぜない。

---

## 5. 調査結果の分類

発見した問題は、必ず次のいずれかに分類する。

### A. 今回直す

今回の目的達成に必須で、修正しなければ不具合や権限問題が残るもの。

### B. 今回は触らず、後続で整理する

今回の目的には直接不要だが、将来の不具合原因になり得るもの。

### C. 意図して残す

互換性、移行期間、既存データ、外部連携等の理由で残すもの。

### D. 削除候補

未使用である可能性が高いが、影響調査後に別タスクで削除するもの。

調査報告には、分類と理由を記載する。

---

## 6. 最小差分の原則

調査で多くの問題が見つかっても、すべてを1つのPRに含めてはならない。

原則：

* 1PR = 1つの目的
* 今回の不具合を直す最小差分
* DB変更とUI変更は必要に応じて段階分割
* 大規模な命名変更を同時に行わない
* 未使用コード削除を不具合修正に混ぜない
* 将来設計を現在のhotfixへ混ぜない
* 通常アカウント、ゲスト、管理者など別導線への影響を抑える

ただし、セキュリティやデータ破損を防ぐために必須の変更は、最小差分より優先する。

---

## 7. 正本

重要な情報には、必ず正本を定める。

正本とは、その情報について最終的に正しいと判断する唯一の基準である。

例：

| 情報               | 正本                                    |
| ---------------- | ------------------------------------- |
| 参加IDの発行元スペース     | `space_participant_accounts.space_id` |
| 参加IDの初回名前登録      | 発行元spaceの `space_nicknames`           |
| 参加IDの所属表示        | `get_my_issued_participant_scope`     |
| 通常アカウントのコミュニティ所属 | `community_memberships`               |
| 通常アカウントのスペース参加   | `space_memberships`                   |

補助データや同期データは、正本の代用として使用しない。

正本が複数存在する状態を新たに作らない。

---

## 8. 不変条件

重要機能には、他機能の変更後も維持する不変条件を記載する。

不変条件の例：

* 参加IDは発行元space以外を所属として表示しない
* 参加IDの初回名前登録判定にusernameを使わない
* nickname hydrate前に未登録判定しない
* 通常アカウント用membership処理で参加IDの所属を決めない
* 発行元以外へnicknameを保存しない
* 発行元以外のpublic閲覧でspace/community membershipを自動作成しない
* 発行元を確認できない参加IDセッションでは自動joinしない
* RPC未存在時に全データへfallbackしない
* 認証前処理に認証済み権限を要求しない

不変条件を変更する場合は、次を同時に行う。

1. 正本仕様書の更新
2. 関連仕様書の整合
3. 回帰テストの更新
4. 変更理由の記録
5. 通常導線・ゲスト導線等の再受入

---

## 9. 必須回帰テスト

重要機能には、仕様書内に必須回帰テストを記載する。

テストは、今回の実装だけでなく、将来の別機能変更でも必ず維持する。

例：

* 未登録参加IDは名前登録画面が出る
* 保存済み参加IDは再ログイン時に名前登録画面が出ない
* 発行元以外のspaceを開いてもmembershipが増えない
* 発行元以外へnicknameを保存しない
* 発行元以外を所属表示しない
* 通常アカウントは複数所属を維持する
* ゲスト導線を壊さない
* loading前の一時状態で誤判定しない
* 異常時に安全でないfallbackを行わない

仕様書に書かれた不変条件には、可能な限り自動テストを対応させる。

---

## 10. 仕様書更新ルール

コード変更時は、関連仕様書を同じPRで更新する。

最低限、次を確認する。

* 正しい挙動
* 正本
* 不変条件
* 必須回帰テスト
* 実装済み / 未実装
* 将来課題
* 通常アカウント等との違い
* 権限
* エラー時の挙動
* loading時の挙動
* データ保存先
* 表示優先順位

仕様書に書かれていることとコードが異なる場合、どちらかを放置しない。

---

## 11. 調査のみタスク

構造が複雑、または次に該当する場合は、実装前に調査だけのタスクを分ける。

* 複数テーブルが関係する
* AuthやRLSが関係する
* Productionデータに影響する
* 複数仕様書が矛盾する
* 正本が不明
* 過去の互換処理が多い
* 変更ファイルが10件以上になりそう
* migrationが必要
* 通常・ゲスト・参加IDなど複数導線がある
* 原因が複数候補ある
* キャッシュとDBのどちらが原因か不明

調査タスクでは、コード・DB・仕様書を変更しない。

---

## 12. 調査報告の必須項目

実装前調査では、最低限次を報告する。

1. 現在の仕様書上の仕様
2. 現在のコード上の仕様
3. DB上の実構造
4. 仕様と実装の不一致
5. 完全なデータフロー
6. 使用しているID
7. 正本
8. 補助データ
9. RLS・権限
10. キャッシュ
11. 古い・未使用・重複構造
12. 今回直すもの
13. 後続で整理するもの
14. 意図して残すもの
15. 最小修正案
16. 安全案
17. 将来案
18. 変更予定ファイル
19. migration / RLS変更の要否
20. 通常機能への影響
21. 小タスクへの分割案
22. 最初に着手する1タスク

---

## 13. 実装完了報告の必須項目

実装後は、最低限次を報告する。

* 根本原因
* 実装方針
* 変更ファイル
* 正本
* 不変条件
* 回帰テスト
* DB変更
* RLS変更
* migration
* Development受入
* 通常アカウント回帰
* ゲスト回帰
* 残課題
* 仕様書更新
* branch
* commit
* PR
* Production反映前の確認事項

---

## 14. Production反映

DB変更を含む場合、次の順序を守る。

```text
merge前レビュー
↓
Production対象確認
↓
migration適用
↓
RPC・DB受入
↓
フロント反映
↓
実画面受入
```

ただし、main mergeでProductionフロントが自動デプロイされる場合は、互換性のある実装にするか、Production DBとの不整合時間を最小化する。

Productionでは次を必ず確認する。

* 接続先
* 未適用migration
* 適用対象
* データ件数
* 適用前後の不変
* CLI linkの復帰
* QAデータの整理

---

## 15. 全体構造整理

個別修正のたびに全体リファクタリングを行ってはならない。

全体整理は、関連機能が安定した段階で別タスクとして行う。

全体整理の成果物：

1. 概念辞書
2. データモデル図
3. ID対応表
4. 正本マトリクス
5. RPC・RLS一覧
6. 作成・更新・削除経路
7. 未使用・古い構造一覧
8. 命名不一致一覧
9. 移行候補一覧
10. 廃止予定一覧

各項目は次に分類する。

* 維持
* 修正
* 統合
* 非推奨
* 廃止候補
* 削除済み

---

## 16. 例外

次の場合のみ、事前構造調査を簡略化できる。

* 文言の誤字修正
* 色や余白だけの変更
* 明確に孤立したUI変更
* テストのみの追加
* 仕様に影響しないコメント修正

ただし、少しでもデータ、権限、ID、状態、保存、取得、ルーティングへ触れる場合は、通常の構造調査を行う。

---

## 17. 最終原則

Hossiiでは、機能が動くことだけを完了条件としない。

完了条件は次のすべてを満たすことである。

* 現在の構造を理解している
* 仕様と実装が一致している
* 正本が明確である
* 不変条件が記録されている
* 回帰テストがある
* 通常導線を壊していない
* 古い構造や矛盾が記録されている
* 今回触らない問題も見失わない
* Productionで確認できている
* 次の変更によって壊れにくい状態になっている
